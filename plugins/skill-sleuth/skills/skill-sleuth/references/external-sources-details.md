- **SKILL.md path (0.3.0).** The SKILL.md of a skills.sh hit is looked up at the pinned sha first on `raw.githubusercontent.com`, in exactly this order: `skills/<skillId>/SKILL.md`, `<skillId>/SKILL.md`, `.claude/skills/<skillId>/SKILL.md`. The first file that returns 200 and carries frontmatter is it; its body is the read itself (no separate request goes out). If none of the three hits, it falls back to the tree API as before. Why: the raw host does not count against the unauthenticated limit; the tree response is large and draws on the quota.
- **Request count (0.3.0).** Describing one hit from a repo not in the cache (new) costs about 2 API requests: repo meta + commit sha (previously 3: + tree). If the first standard path misses, 1-2 more raw requests go out; if all three miss, the tree API and one raw request are added. A raw attempt that misses on the standard path does not count against the request budget (at most 9 per run). In `--query` the tree request is only this fallback path; `--show` still uses the tree API for the file list (and `--show community:<plugin>`). While the cache is fresh, a repeated search never reaches the GitHub API. The upper bound the script documents (cold `--query`, default `--describe 3`): at most 9 API requests if the described files are on the standard path (`--top 6`); otherwise at most 10 (`--top 6`, default source), 11 with `--source skills.sh`; at most 13 whatever `--top` is (0.2.1's upper bound).
- **Cache lifetimes (`dis_kaynak_github.json`).** Repo meta (stars, forks, dates, archive, license) 7 days; the commit sha of a floating HEAD 60 min; lookups at a pinned sha 24 h (file list and SKILL.md paths, which standard path hit, the path's first commit). The `YENI` (new) age is computed from the creation date at run time; the cache does not age it.
- Do not use: `https://skills.sh/api/v1/skills/<owner>/<repo>/<skill>` and `/api/v1/skills/search` → 401 `authentication_required` (asks for a Vercel OIDC token). Do not request or add a token.
- Where "What it does" comes from: since the skills.sh search has no description, the SKILL.md frontmatter `description` at the pinned commit; if the limit is exhausted or the path was not found, the first non-empty audit `summary`; if that is also missing, `alinamadi` (could not be obtained). For a community hit, the first sentence of the catalog `description`.
- `riskLevel` observed values: `SAFE`, `LOW`, `NONE`, `MEDIUM`, `HIGH`; the field may be absent entirely (Socket). `CRITICAL` was not observed (unverified). 5 providers observed: Gen Agent Trust Hub, Socket, Snyk, Runlayer, ZeroLeaks.
- `claude-community`: authors submit their plugin to Anthropic; every listed entry has passed automated security scanning and been approved for distribution, and the catalog is synced nightly from Anthropic's internal review pipeline (catalog README, re-read 2026-10-10). Anthropic does not maintain the plugins or vouch for the code: per the official trust warning it does not control plugin contents and cannot verify they will work as intended or stay unchanged (code.claude.com/docs/en/plugins/security). Short form: "scanned and approved by Anthropic; it does not vouch for the code". Where the catalog pins an entry to a commit sha (nearly all), Claude Code refuses to install a different commit. Call forms (use no other form; `<skill_dir>` = the "Base directory for this skill:" line):

```
PYTHONUTF8=1 python "<skill_dir>/scripts/dis_kaynak_ara.py" --query "<2-6 English keywords>" [--top 6] [--source all|skills.sh|community] [--describe 3] [--desc-len 160] [--max-bytes 2048] [--new-days 90] [--min-installs 1000] [--min-stars 100] [--all] [--json] [--refresh]
PYTHONUTF8=1 python "<skill_dir>/scripts/dis_kaynak_ara.py" --show <owner/repo/skill | community:<plugin>>
PYTHONUTF8=1 python "<skill_dir>/scripts/dis_kaynak_ara.py" --audit <owner/repo/skill>
PYTHONUTF8=1 python "<skill_dir>/scripts/dis_kaynak_ara.py" --repo <owner/repo | https://github.com/owner/repo[.git]>
```

- `--query`: text output; `--max-bytes` (default 2048, minimum 300; below that exit 2) is enforced hard by dropping trailing hits whole. `--top N` is the number of hits examined (remaining + eliminated); with a large `--top` the last 8 requests are reserved for describing the first hits, and the stars / age of hits whose turn does not come stay `dogrulanamadi` (could not be verified) (reason: `istek butcesi` (request budget)). `--describe N`: sha, path, description and audit query only for the first N shown, non-eliminated skills.sh hits (default 3; repo meta is fetched for every examined hit); the others get `ne yapar: (aciklama icin --show)` (what it does: run --show for the description), `denetim=bakilmadi` (audit=not checked), `@(sha icin --show)` (run --show for the sha) (§3.2 "Additional markers").
- `--query` hit lines carry installs, stars, repo age, last push and labels (§3.2). Eliminated hits move below the `-- elenenler (yeni / populer degil): --` separator line (eliminated (new / not popular)) and are printed as a single line (identity + labels + reason); `--all` prints them in full too. Order of the remaining ones: unlabeled hits first, then those with soft warnings (any label or `dogrulanamadi`); at each level skills.sh hits with installs above the threshold first (within a group the script's search order is kept: API order + name match + a small install weight), community hits by descending stars; the two registries are interleaved in order.
- `--new-days`, `--min-installs`, `--min-stars`: flags for the thresholds in the core §3.1 table, defaults equal that table (`YENI` and `SKILL-YENI` → `--new-days 90`; `AZ-KURULUM` (few installs) → `--min-installs 1000`; `AZ-YILDIZ` → `--min-stars 100`; `BAYAT` (stale) is fixed at 365 days, no flag; `ARSIV` (archived) has no flag). Do not pass them unless the user explicitly states a different threshold; `--all` only when the user wants to see the eliminated ones in full. Why: relaxing a threshold silently switches the protection off. If a threshold differs from the default the script prints a `not: esikler varsayilan degil: …` line (note: thresholds are not default) (§3.2).
- `--show`: single entry, ≤ 2 KB (description, source URL, sha, SKILL.md path, raw URL, audits, install command; also stars, repo age, labels and `skill ilk commit` = the first commit date of the skill file, which is where `SKILL-YENI` comes from). `--audit`: one line per provider.
- `--repo`: single block, ≤ 500 bytes: `yildiz` (stars), `fork`, `olusturulma` (created; date + age), `son push` (last push), `arsiv` (archived), `lisans` (license), then labels (`etiket:`) and the script's verdict (`elenir:` (eliminated:)). One GitHub request, 7-day cache. It does not ask for search consent (core §2 item 4): get a layer 2-3 candidate's stars and age with this. This mode does not know the install count or the candidate's source: you add `AZ-KURULUM` and the elimination it forms, and case 5 on a counter-less source (§3.1). The last line reminds you of this in the form `elenir: hayir (…)` (eliminated: no (…)): if the output has `AZ-YILDIZ` or stars / age could not be obtained, the candidate is eliminated on a counter-less source (case 5); it is also eliminated if installs are below the threshold (case 3 with `AZ-YILDIZ`, case 4 with unobtainable stars / age).
- 15 s timeout per request; the per-run request budget is fixed in the script (at most 18 requests counted against the budget, repo meta included; at most 9 raw attempts missing on the standard path are not counted: at most 27 requests go out. Describing is either done in full or not started: a hit whose worst case, i.e. commit sha + file list + SKILL.md + audit, does not fit the remaining budget stays `bakilmadi`; measurements in `scripts/README.md`), User-Agent `skill-sleuth/0.1 (+skill search)`. Repo meta is cached for 7 days; the second run does not reach GitHub. `--refresh` ignores all caches.
- The script cleans every text it fetches (description, audit summary, name, path) before printing: invisible characters (control, zero-width, bidi, tag block U+E0000-E007F, private use, lone surrogates) become spaces. If 8 or more characters were removed from one field, a `not: <id>: N gizli karakter silindi (kirmizi bayrak)` line appears (note: N hidden characters removed (red flag)) (§3.2). Why: so that hidden text does not leak into the context as an instruction, and its removal is not hidden either.

## 2. Consent and privacy

The rules are in core §2 (when it runs (a)/(b)/(c), the numbered question, the one-line announcement, query privacy, the `--repo` exception). Here are examples, reasons and the script's own protection.

- **Limit of the single network exception.** `dis_kaynak_ara.py` is the skill's ONLY script that goes out to the network: token-less read-only GET only to `skills.sh`, `api.github.com`, `raw.githubusercontent.com`; a redirect to another host is refused. The only place it writes is the cache: %TEMP%\skill-sleuth on Windows (`%TEMP%` is per-user), ~/.cache/skill-sleuth on macOS/Linux (`$XDG_CACHE_HOME/skill-sleuth` when `$XDG_CACHE_HOME` is set; since 0.4.0, created with mode 0700); changed with `--cache-dir` or `$DIS_KAYNAK_CACHE_DIR`. A cache path pointing into the skill folder or a Claude config tree (`~/.claude`, any `.claude` folder, `$CLAUDE_CONFIG_DIR`, `$CLAUDE_CODE_PLUGIN_CACHE_DIR`) is refused (exit 2) before any folder is created. A cache directory or file not owned by the current user, or group/world-writable, is not used, and a symlinked temp file is never followed: the script does not crash, it runs without the cache and warns. Why: in a shared `/tmp` another user could plant fake stars / age and get past the elimination. It runs no installer (no `npx`, no `claude plugin …`), writes nothing under `~/.claude`. The other scripts never go out to the network. Why: so the single point that reaches the network stays auditable.
- **What counts as an (a) request:** "look on skills.sh", "search for skills on GitHub / in the community", "also look at third-party sources", "look everywhere" while searching for a skill. **What does NOT count as a request:** the word GitHub or community appearing as the subject of the task ("review the PR on GitHub", "clone this repo", "fix my GitHub Actions workflow"); a specific repo URL being given ("<url> install this": not a search but a direct §4 review and consent); a request given for a previous task (it does not carry over to this task).
- **(b) explicit skill search:** "is there a skill", "find a suitable skill", "also look at ones that are not installed". Work that finishes plainly with built-ins: web research, question-and-answer, a small edit. The (b) question is the only exception to the "no question" rule in fail-open; if the work finishes plainly with built-ins there is no question, (c) applies. No script until "1" arrives. "2" → fail-open; do not ask again in the same task, and do not write the report line from (c) either.
- **(c) why:** a result was requested; in work the built-ins suffice for, a third-party candidate is never chosen anyway (SKILL.md Step 3), the question wastes a turn.
- **Mode.** claude.ai chat (C) and `--bare` (B): the layer never runs, no question. D/N/X: it runs. W (Cowork): not measured (unverified); skip if there is no `Bash` + network.
- **Scope.** If the user said "I don't want third-party" in this session, (a) and (b) drop too, and the report line from (c) is not written either. Search consent covers only the search; use is a separate consent (§4). Consent is for that task; it is not generalized across the session.
- **Query examples.** Good: `pdf table extract` · `code review` · `git commit message` · `c# unit test`. Bad: `Q3_sales_report.xlsx table` (file name) · `D:/accounting/invoice.pdf` (path) · `jane@company.com crm` (e-mail) · `order 20261005` (number from data) · `acme logistics contract` (customer name: the script does NOT catch it, you eliminate it). Why: the query lands in the third party's server log. Never goes in: a file name or path, a customer/person/company name, an internal project or product code name, the user's repository name, an e-mail, a URL, a number from the user's data, text copied from a document.
- **Script protection.** The query is accepted only if it matches the pattern `^[letter digit space + # -]{2,80}$` (Unicode letters allowed; no underscore, `/`, `\`, dot, colon, `@`), at most 8 words, no digit run of 5+ digits, at most 6 digits in total, at most one digits-only word (a phone / order number split by spaces does not pass either); otherwise it writes the rule on one line and exits 2. The protection is a net, not the rule: a proper name that passes the pattern still does not go out.
- **The `--show` / `--audit` identifier** also goes out to the network (skills.sh, api.github.com): copy the identifier only from previous search output or use the `owner/repo/skill` the user typed themselves; do not derive an identifier from user data (file, folder, project name). Why: the script cannot tell a path-like identifier apart if it has no file extension.
- **With `--source community`** the keyword never leaves the machine (the whole catalog is downloaded, searched locally); use this if the user does not want a query sent to skills.sh.
- **Why `--repo` asks no consent.** It sends a single GET only to `api.github.com/repos/<owner>/<repo>`; the only thing that leaves the machine is a public repo name (no keyword, query or user data goes out). That is why, as part of the read-only pre-install review of a layer 2-3 candidate (official catalog, claude.ai directory), it may run WITHOUT the consent in core §2 item 2; `security-review-details.md` "Pre-install review" step 5 already reads the same host. Why: without stars and age the §3.1 lines cannot be written; a public repo name is not user data.
  - The repo name comes only from: the catalog record (`skill_ara.py --show <plugin>` → `source_url`), `upstream.repo_url` in the `SearchPlugins` record, previous search output, or the repo address the user typed themselves in this task. Do not derive a repo name from user data (file, folder, project name). A connector's `url` (a remote MCP server) is not a repo: never pass it to `--repo`.
  - Only for a not-installed candidate you will show the user, once per candidate, at most 3 candidates per task. If the candidate will not be shown (fail-open, implicit work, exact match in the listing) do not run it. In an implicit job (the user did not ask about skills or plugins) never run it, no network request the user did not ask for: a layer 2-3 candidate that needs `--repo` counts as unmeasured and is not named; the report says at most "an installable plugin may fit; I can check if you want". Why: the 60 requests/hour limit is shared with every session on the same IP.
  - `--query`, and `--show` / `--audit` for a skills.sh / community hit, still ask for the consent in core §2 item 2; having run `--repo` does not open the third-party search.
  - It does not run in modes C and B. If the user said "don't go online", do not run it: as in an implicit job the candidate counts as unmeasured and is not named ("k candidates not measured"; `modes.md` "Offline request").

## 3. Presenting results

The raw script output stays in the context, it is not printed to the user. Core §3.1 is the single source of truth for the popularity, age, label and elimination rules of every NOT-installed candidate (layer 2 catalog / marketplace, layer 3 claude.ai directory, layer 5 third-party; except layer 3's connector sub-step: §1 "Popularity and age data" note): `security-checklist.md` and `routing-patterns.md` refer to it; if you see a difference between the script defaults and the table, the table prevails, state the difference in the report. §3.2-§3.4 are the presentation of layer 5 output.

### 3.1 Signals, labels, elimination: details and measurements

The label table, the five elimination cases and the "what to do" rules are in core §3.1. Here are the edge cases, reasons and measured examples.

- **A signal that cannot be obtained.** Write "could not be verified"; do not guess, do not silently skip the line. Why: a field left empty reads as "no problem". If none of the labels applies write "Labels: none".
- **Where the lines come from.** Installs: `unique_installs` in the official catalog, `installs` on skills.sh; the community catalog has no counter, write "no install data". Stars are repo-level: if the repository hosts more than one skill or plugin add "(repo-wide)". Last update: `last_updated` in the official catalog, last push elsewhere. Pass the age on as the script writes it: days below 90 days, months below 2 years, years above that. Which signal comes from where is in the §1 "Popularity and age data" table.
- **The `./plugins/…` source.** If the `source_url` that `skill_ara.py --show` gives is not a GitHub repository (`./plugins/…`: the plugin lives inside the official marketplace repository; 53 entries in the snapshot) do not run `--repo`: write "stars: no separate repo (lives in the official marketplace repository)", derive the labels only from `unique_installs` and `last_updated`.
- **Why case 4.** The only measurable sign of popularity is bad and there is no signal to balance it; for a low-install candidate to stay, both stars and age must be verified. Reasons for not obtaining them: the source is not a GitHub repository; the repository was not found; GitHub limit or network outage; `--repo` could not be run; request budget with a large `--top`.
- **Case 4 does NOT apply to:** a candidate with installs above the threshold (31,764 installs + stars could not be verified = soft warning); a candidate with no install count or an unreadable one (community catalog, claude.ai directory: "no install data" and "could not be verified" for installs do not produce `AZ-KURULUM`; for a counter-less candidate see case 5); a plugin that lives inside the official marketplace repository (`./plugins/…`: "no separate repo" is not a "could not be verified").
- **Why case 5.** On a counter-less source the only popularity evidence is stars; if that too is below the threshold or could not be verified (GitHub limit, network outage, repository not found, `--repo` could not be run, a catalog entry with no repository of its own) there is no data at all showing that anyone has tried the candidate. Before 0.4.0 a counter-less candidate with unverifiable stars was shown with a soft warning; that contradicted the owner's decision "nothing new and unpopular is recommended", so it is now eliminated (with the 60 requests/hour quota shared, this case is not rare). Scope: a community catalog hit (`kurulum=veri-yok` in the script (installs=no data)); an entry in the official catalog without the `unique_installs` field (6 entries in the snapshot, e.g. `notion`).
- **Case 5 does NOT apply to:** a candidate with an install count (a skills.sh hit; an official entry with `unique_installs`): if installs are above the threshold `AZ-YILDIZ` or "stars could not be verified" stays a soft warning (measured: 9,468 installs + 54 stars → `etiket: AZ-YILDIZ(54)`, full block), if below, case 3 or 4 operates; a candidate whose installs are "could not be verified" (a counter exists, it could not be read: claude.ai directory): soft warning; a plugin that lives in the official marketplace repository (`./plugins/…`): "no separate repo" is not a "could not be verified", its labels come from `unique_installs` and `last_updated`.
- **Result of case 5.** Most community hits are below 100 stars, so they mostly appear only on the `Eliminated:` line. Measurement (2026-10-05, script 0.2.1, warm cache): 22 of the 24 community repositories whose stars were measured are below the threshold (the highest 62 stars). `--query "code review" --top 4` → the 2 skills.sh hits with installs as full blocks, the 2 examined community hits below the separator: `- community:code-review-harness  AZ-YILDIZ(0)  (kurulum sayaci yok + az yildiz)` (no install counter + low stars) and `- community:outside-in-code-review  AZ-YILDIZ(1)  (kurulum sayaci yok + az yildiz)`. `--query "supabase migration" --source community` → 5 of 5 hits eliminated (0, 0, 28, 36, 45 stars); the output starts with `not: guvenilir populerlikte aday yok: 5 isabetin hepsi elendi (tam gorunum: --all)` (note: no candidate with trustworthy popularity: all 5 hits eliminated (full view: --all)). A community hit that passes the threshold is unaffected: `--query "superpowers" --source community --top 3` → `superpowers` (295,394 stars) full block, the two hits with 0 and 10 stars below the separator.
- **What the user can do.** They can request an eliminated hit by name (full block + bold warning) or relax the threshold by stating it themselves (`--min-stars N`; the script prints `not: esikler varsayilan degil: …`); do not relax it on your own.
- **Label value.** Every label outside these and a standalone "could not be verified" is a soft warning. Write the label with its measured value: the script prints `YENI(41 gun) AZ-YILDIZ(12) AZ-KURULUM(43)` (gun = days), you tell the user "41-day-old repo, 12 stars, 43 installs".
- **Why the elimination rule.** Nobody has tried a new and unpopular skill yet; it has not seen enough users and time for it to turn out useless, abandoned or harmful. Stars and install counts are imperfect proxies and can be inflated: that is why they only gate the recommendation and never replace the security review (`security-checklist.md`).
- **"Could not be verified" and `BAYAT`.** Alone it counts neither as eliminated nor as having passed the threshold: the candidate may be shown, the field is written "could not be verified", it is a soft warning; neither can be the default choice while an unlabeled alternative exists. Two exceptions: case 4, and case 5 on a counter-less source; then write the measured value and the reason on the `Eliminated:` line; if the reason is the GitHub limit or a network outage, say it can be looked at again once verified (not when the source is not a GitHub repository or the plugin is stored inside the catalog repository: that reason is lasting): `Eliminated: <name> — 269 installs; stars and age could not be verified (GitHub limit), can be looked at again once verified` · `Eliminated: <name> (community catalog) — no install counter, stars could not be verified (GitHub limit), can be looked at again once verified`. If requested by name, again a full block and a bold warning.
- **`AZ-YILDIZ` or unverifiable stars on a counter-less source.** The candidate is eliminated, the §4 dialog is not opened; write "no install counter, N stars" or "no install counter, stars could not be verified" on the `Eliminated:` line. If requested by name, the Popularity line in the full block becomes "no popularity evidence: no counter, N stars" (or "…, stars could not be verified") and the bold warning follows. Never guess the stars, never relax the threshold. Why: there is no data besides stars to tell apart a plugin nobody has tried; without stars there is no data at all.
- A candidate with a soft warning may be recommended; state its label by name and value, put the unlabeled candidate at the same level first (`routing-patterns.md` §2.2).
- **Layer 2-3 candidate.** The same labels are derived from `unique_installs` / `last_updated` and the `--repo` output; being in the official catalog does not lift the elimination. `--repo` does not know the install count: even if it writes `elenir: hayir`, add `AZ-KURULUM` yourself if `unique_installs` is below the threshold and re-apply the five cases; on an entry without the `unique_installs` field, if `--repo` shows `AZ-YILDIZ`, case 5: the candidate is eliminated for "no install counter, N stars". Measured example (2026-10-05): `pendo-analytics` in the official catalog, 7 installs, last update 2026-09-21; its source repository `pendo-io/claude-pendo-plugin` 1 star (repo-wide), repo 2026-02-25 (7 months). `--repo` alone sees only `AZ-YILDIZ`; together with the 7 installs from the catalog, `AZ-KURULUM` + `AZ-YILDIZ` = eliminated. If `--repo` gave no output (exit 3, GitHub limit, could not be run) and `unique_installs` is below the threshold, case 4: the same candidate is again eliminated for "7 installs; stars and age could not be verified"; if the field is missing, case 5: eliminated for "no install counter, stars could not be verified"; if `unique_installs` is above the threshold, it is a soft warning.

### 3.2 Raw line mapping (`--query`)

The header line carries the hit count per source, the Anthropic warning for the registry (skills.sh: `UCUNCU TARAF - Anthropic incelemedi` (THIRD PARTY - not reviewed by Anthropic); community catalog: `TOPLULUK KATALOGU - Anthropic taradi ve onayladi; kodu garanti etmez` (COMMUNITY CATALOG - scanned and approved by Anthropic; it does not vouch for the code); 0.4.0) and, when known, the `GitHub kalan: R/60` value (GitHub remaining). Pass the warning on to the user in plain English (the §3.3 `Tier:` line). The first lines per hit:

```
1. [skills.sh T5] owner/repo/skill  kurulum=N  yildiz=S(repo)  repo=YYYY-MM-DD(<age>)  son-push=YYYY-MM-DD  denetim=...
   etiket: -            (or: etiket: YENI(41 gun) AZ-YILDIZ(12))
2. [topluluk T4] <plugin>  kurulum=veri-yok  yildiz=S  repo=YYYY-MM-DD(<age>)  son-push=YYYY-MM-DD
```

A value that could not be obtained is printed as `dogrulanamadi`. Below them come the `ne yapar:` (what it does), `kaynak:` (source) and `kur (...)` (install) lines.

Mapping (raw field → block field):

- `[skills.sh T5]` / `[topluluk T4]` (community T4) → Registry + Tier.
- `kurulum=N` (installs) → Popularity "N installs (skills.sh counter)"; `kurulum=veri-yok` → "no install data (no counter in the catalog)". A `kurulum=veri-yok` hit that arrives as a full block has measured stars above the threshold; the script moves one below the threshold, or one whose stars could not be verified, under the separator by case 5 (0.4.0).
- `yildiz=S(repo)` (stars) → "S stars (repo-wide)"; `yildiz=S` → "S stars". The script puts the `(repo)` suffix on a skills.sh hit and on a community plugin that sits in a subdirectory of its repository.
- `repo=YYYY-MM-DD(<age>)` → Age "repo YYYY-MM-DD (<age>)"; `son-push=YYYY-MM-DD` (last push) → "last update YYYY-MM-DD".
- `etiket: -` (labels) → "Labels: none"; `etiket: YENI(41 gun) AZ-YILDIZ(12)` → "Labels: YENI (41-day-old repo) · AZ-YILDIZ (12 stars)". The `(yildiz/yas dogrulanamadi[: <reason>])` note at the end of the line (stars/age could not be verified) = those signals could not be obtained: do not write "Labels: none" and move on, write "could not be verified" on the Popularity and Age lines.
- `dogrulanamadi` in any field → "could not be verified" (a soft warning on its own; the script already moves a hit with installs below the threshold under the separator by case 4, and a counter-less hit by case 5).
- `denetim=pass(Socket),fail(Snyk)` (audit) → Audit; `denetlenmemis` (skills.sh 404) → "unaudited"; riskLevel is only in `--show` / `--audit` output, if you are writing from `--query` do not add the parenthesis, do not invent it.
- `ne yapar:` → What it does · `kaynak: <url> @<sha12>  yol: <...>` (yol = path) → Source.
- The `kur (...)` line does not enter the block, it is used in §4: `kur (iki ayri onay)` (install (two separate consents)) = sha-pinned T4 (Claude can install with two consents), `kur (sha-yok: Claude kurmaz; kullanici calistirir)` (install (no sha: Claude does not install; the user runs it)) = T4 but no pinned commit (do not offer that Claude installs it), `kur (kullanici calistirir)` (install (the user runs it)) = T5.
- Every line below the `-- elenenler (yeni / populer degil): --` separator line (identity + labels + elimination reason in parentheses) is an eliminated hit: write no block, carry it only to the `Eliminated:` line. Translate the reason into plain English: `(kurulum sayaci yok + az yildiz)` → "no install counter, N stars" (case 5); `(kurulum sayaci yok, yildiz dogrulanamadi[: <reason>])` (no install counter, stars could not be verified[: reason]) → "no install counter, stars could not be verified[ (<reason, plain English>)]" (case 5; only when the reason is `GitHub siniri` (GitHub limit) or `GitHub ulasilamadi` (GitHub unreachable) add "can be looked at again once the limit resets / the network is back"; the budget reasons `istek butcesi` (request budget), `istek butcesi doldu (N)` (request budget used up) and `sure butcesi doldu (N sn)` (time budget used up (N s)) → "request/time budget used up" (this run's budget) and add "can be looked at separately" (the hit is looked at on its own with `--show <id>`); never for a lasting reason such as `GitHub deposu degil` (not a GitHub repository) or `katalog deposunda barinir…` (stored inside the catalog repository)); `(GitHub-disi kaynak + az kurulum)` (non-GitHub source + low installs) → "N installs, not a GitHub repository (stars and age could not be verified)" (case 4).
- `GitHub kalan: R/60` = the remaining unauthenticated GitHub quota (per IP, hourly; shared with all sessions on the same IP). Do not print it to the user; if R is 5 or below, do not run additional `--show` / `--repo`, write the missing signal as "could not be verified". When the limit is hit the note line also gives the reset time (`sifirlanma ~SS:DD` (reset ~HH:MM)): tell the user that time.

Additional markers (seen in live output):

- `ne yapar: (denetim ozeti: <provider>) …` (in `--show`: `ne yapar (denetim ozeti: <provider>): …`) (denetim ozeti = audit summary) = the author's description could not be obtained; the text is the audit provider's summary. End the "What it does" line with `(auditor summary: <provider>; author description could not be obtained)`, do not write "(the author's own statement)". Take only the function from the summary; do not carry a security or praise verdict such as "safe", "robust", "no issues" (that is the "Audit" line's job). Why: a description with a misattributed source breaks the "state the source" rule.
- `ne yapar: (aciklama icin --show)` + `denetim=bakilmadi` + `kaynak: … @(sha icin --show)` = this hit was not looked at at all (`--describe` or the byte limit): no description, sha or audit. If you will show it, first run `--show <id>` and fill the block from that output: only for the hit you will show, once per hit, at most 3. The search consent covers this (only the hit's own identifier goes to the same three hosts); it does not count toward the two-`--query` limit in §5. If you will not run it, do not show it, count it in the "<k> more hits" line. Never write `bakilmadi` as "unaudited"; do not treat `@(sha icin --show)` as "no pinned commit". Why: "unaudited" is a measured result (skills.sh 404); "not checked" means it was never asked, there may be a fail / HIGH behind it.
- `denetim=alinamadi` (in `--show`: `denetim: alinamadi`) = the audit query failed: write "Audit: could not be obtained"; do not say "unaudited" or "clean".
- `@sha-alinamadi (<reason>)` (sha could not be obtained; in `--show`: `@sha alinamadi`), `https://skills.sh/<id>  (GitHub deposu degil; sha yok)` (not a GitHub repository; no sha), in community `@sha-yok` (no sha) and `(ref=<ref>, sabit degil)` (not pinned) = no pinned commit; §3.4 "If there is no pinned commit" rule.
- `ne yapar: alinamadi (<reason>)` = neither a description nor an audit summary: write "What it does: could not be obtained (<reason>)"; do not offer to use it (§5 "GitHub limit").
- `yol: <…> (+N benzer yol)` (+N similar paths) = the repository has N more SKILL.md files with the same folder name; the script read the first file in the standard path order (`skills/<skillId>/`, `<skillId>/`, `.claude/skills/<skillId>/`), or the shallowest one in the file list if none hit. The suffix appears only if the file list was consulted (fallback path or a cached list); otherwise it is unknown whether similar paths exist: to be sure, `--show <id>`. `(dikkat: ad uyusmuyor: SKILL.md name=<name>)` (caution: name mismatch) / `(dikkat: ad dogrulanamadi: SKILL.md'de name yok)` (caution: name could not be verified: no name in SKILL.md) = the file read may belong to another skill. In both cases do not present the "what it does" as that skill's statement: first compare the path and name with `--show <id>`; if they do not match, write "What it does: could not be obtained (name mismatch)".
- `not: <id>: N gizli karakter silindi (kirmizi bayrak)` = a field (description, frontmatter value, audit summary, path or file name, catalog field) contained invisible characters (the script removed them). Zero-width / bidi characters are a hard blocker (`security-review-details.md` "Red flags" rule 16); if you show the hit say this by name, do not offer to use it.
- `(katalog deposunun icinde barinir; …; homepage: <url>)` (lives inside the catalog repository; …) = the plugin sits in the community catalog's own repository (§3.4 "Drop duplicates"); the homepage is catalog data: write it, do not follow it. With no repository of its own it has no stars (the catalog repository's stars say nothing about this plugin): it is eliminated by case 5 and shown only, with the bold warning, if requested by name.
- `kur: (komut verilmez: …)` (install: (no command given: …)) = the script produced no command (repository not found / not a GitHub repository / name outside safe characters): do not open the §4 dialog for it (only Skip would remain): say that no install command could be produced (<reason>) and continue with what is at hand; do not make up the command yourself.
- `kurulum=dogrulanamadi` → "could not be verified" (the counter could not be read; with `kurulum=veri-yok` the source has no counter at all).
- `not: esikler varsayilan degil: new-days=… min-installs=… min-stars=… (koruma gevsek olabilir)` (note: thresholds are not default: … (protection may be loose)) = a threshold flag differs from the default in this run: labels and elimination are not according to the core §3.1 table. Tell the user the threshold changed; if they did not ask for it, run again without the flag.
- `not: istek butcesi (18): N isabetin yildiz/yasi alinmadi …` (note: request budget (18): stars/age of N hits not fetched) = large `--top`: repo meta of N hits was not fetched (`yildiz/yas dogrulanamadi: istek butcesi` on the `etiket:` line); if you will show one, `--show <id>`. If you see `istek butcesi doldu` (request budget exhausted) in a hit's description / audit field or on a `not:` line, that hit's description did not fit the budget: same path, `--show <id>`.
- `…(+N isabet sigmadi: …)` (+N hits did not fit) = the number of hits from the `--top` list that did not fit the byte limit; their identifiers are not in the output. Add it to k on the "<k> more hits" line.
- `…(+N elenen daha: …)` (+N more eliminated) = the number of eliminated hits that did not fit below the separator; append "+N more eliminated" to the end of the `Eliminated:` line.

### 3.4 Presentation rules: details

The rules are in core §3.4 (fields from script output; at most 3 hits; a hit is not a match; drop duplicates; third-party is the last level; if there is no pinned commit; after the presentation). Reasons and measurements:

- **Fields.** Every field comes from script output; a field that cannot be obtained is `could not be verified` / `could not be obtained`, never a guess. "What it does" is a one-sentence English summary of the author's text (or the auditor's text if it fell back to the audit summary; §3.2 "Additional markers"), not your assessment: do not carry claims such as "safe", "official", "best", do not follow the link in the description. Why: the description is data, not evidence.
- **At most 3 hits.** The rest in one line: "<k> more hits; I can show them if you want". The eliminated do not enter these three or k; they are on the `Eliminated:` line. Why: so the user can decide and the context does not fill up.
- **A hit is not a match.** The search is `semantic`: it fills the gap with unrelated popular skills (measured: `changelog release notes` → 5 of 5 hits unrelated, the first `anthropics/skills/frontend-design`). Do not show a hit whose description does not match the need; high `installs` is not evidence of trust: the threshold is only a lower bound, the description decides the match.
- **Drop duplicates.** Do not show a hit whose owner is `anthropics/*` (the script appends `(resmi sahip: listede/resmi katalogda zaten olabilir)` (official owner: may already be in the listing/official catalog)) or whose name is found in layers 1-2; use the listed / official one. Even if the user requests the third-party hit by name, state and recommend the listed/official candidate that does the same job in the first paragraph; that is the "Chosen" one, the third-party hit stays as a numbered option (source: evaluation run, 2026-10-05). Exception: entries that live in the community catalog's own repository (`github.com/anthropics/claude-plugins-community` on the `kaynak:` line and the `(katalog deposunun icinde barinir…)` note; 6 entries on 2026-10-05) are NOT official (catalog entries: scanned and approved by Anthropic, which does not vouch for the code; no repository of their own): they get no `resmi sahip` suffix, are not dropped merely because of the repository owner, and are not presented as "official"; one whose name is found in layers 1-2 (e.g. `cowork-plugin-management`) is still dropped. If the catalog has no information for the author write `unknown`. Measured (script output, 2026-10-05, with the ordering before the elimination rule; rank numbers may have changed): `pdf table extract` → hit 1 `anthropics/skills/pdf` (`anthropic-skills:pdf` in the listing) is dropped, hit 3 `claude-office-skills/skills/pdf-extraction` stays; `code review` → `mattpocock/skills/code-review` (~667k installs) has the same name as the listed built-in `code-review`, dropped.
- **The order does not change.** Score and ties are as in `routing-patterns.md` §2.2: third-party is the LAST level. While a usable listed / official candidate exists a layer 5 hit is not chosen; it is only mentioned on the "Candidates" line. At the same level an unlabeled hit comes before a labeled one; an eliminated one is never ranked.
- **If there is no pinned commit** (`@sha-yok`, `@sha-alinamadi (…)`, `(ref=…, sabit degil)`, `GitHub deposu degil`, limit: in short, if there is still no `@<12-char sha>` after `--show`) write `no pinned commit` on the "Source" line; for that hit do not offer that Claude installs it (for a community entry the script also says this with the `kur (sha-yok: Claude kurmaz; kullanici calistirir)` tag). `@(sha icin --show)` does not fall under this rule: `--show` first. Why: the T4 condition is "sha must be pinned"; unpinned content can change after the review.
- **After the presentation.** If there is a single suitable (non-eliminated) hit, do the §4 review in the same turn and end with the two-option question; if there are several suitable hits ask "Which one should I review? 1/2/3 · 4. None", end the turn. If only eliminated ones remain, ask no question. A hit carrying `AZ-YILDIZ`, or with stars that could not be verified, on a counter-less source does not count as suitable: it is eliminated (case 5), it enters only the `Eliminated:` line. Why: the review is per hit; the user picks which one is reviewed.

## 4. Ways to use

Using a hit ALWAYS requires its own numbered consent; the search consent and "install" / "use" in the prompt are not consent. ONE hit at a time. The two-option question and the risk level rule are in core §4. Order:

1. For a registry hit get the single entry with `--show <id>` (stars, repo age, labels and `skill ilk commit` are here too); on a repo URL the user gave themselves do not run `--show`/`--audit` (the name goes to skills.sh): only `--repo <owner/repo>` and reading `raw.githubusercontent.com/<owner>/<repo>/<sha>/…` at the pinned sha, take the sha from `api.github.com/repos/<owner>/<repo>/commits/HEAD`; apply `security-review-details.md` "Pre-install review" steps 3, 5, 6 at the pinned sha (for a T4 plugin including `.claude-plugin/plugin.json` and its `dependencies` list, `hooks/hooks.json` and the mod code (JS) it points to, `monitors/monitors.json`, `.mcp.json`, `.lsp.json`, `bin/`, a root `settings.json`; every code-running component and every dependency is named in the consent block); classify with "Red flags" in the same file and `security-checklist.md` "Hard blockers (8)".
