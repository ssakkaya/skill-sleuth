# Changelog

## 0.1.1 — 2026-10-14

Preparation for the Claude plugin directory: a narrower description, no manual following of remote third-party skills, disclosures, a license in each plugin folder, less local data, and safer, more accurate scripts (`skill_ara.py` 0.6.3, `dis_kaynak_ara.py` 0.4.2; `builtins.json` is unchanged).

### Added

- Layer 3 also searches the claude.ai connector directory (`search_mcp_registry` of the `mcp-registry` MCP server; observed in the Desktop Code tab on 2026-10-14, unverified in claude.ai chat, not seen in the terminal) when a task needs a service, such as a calendar, that no tool in the session covers and that is not only waiting for you to authorize it or failing to connect (a server that failed to connect is reported for you to fix or retry with `/mcp` or the claude.ai connector settings; no search, no card), even when a listed skill fits: at most one search per task with at most 4 English words (the service's public product name and one generic noun; the name of an internal or private system is left out; never personal data, names of people, customers or projects, file names, paths, URLs or e-mail addresses), which go to claude.ai. The whole result, with every match's connection flag, returns into the conversation like any tool result; Claude repeats only the name, a short description, the connected flag, the directory id and the server host, and never prints the raw response. A directory connector has no repository or counters, so it gets no star/age check and no elimination; it is shown with its server host and a note that the directory gives no publisher, popularity or age. Row 17 of the sources reference (`kaynaklar.md` / `sources.md`) describes the tools and their result fields.
- Path I: for a matching connector that is not connected, at most one `suggest_connectors` card per task with up to 3 connectors; it is not repeated after you ignore it and is not shown after you said nothing should be installed or connected, or in an unattended run (one search is still allowed there, only to name the connector on the Persist line). You click Connect; the service may show its own permission screen, where you approve the permissions (unverified; only the card was observed). Once connected, the connector's server can read and act on (write or delete in) your account on that service, within the permissions you approve. Claude never connects or turns on a connector itself and never asks for or handles credentials. Whether a connector connected this way works in the running session is unverified (otherwise a new session). A connector that is connected on the account but whose tools are missing in the session is reported as not active here, for you to turn on. Precedence: a listed skill that uses an already-connected tool, then a skill or plugin that covers the workflow (the connector becomes its prerequisite), then a bare connector. `list_connectors` and the card's re-authorization use are not used. The plugin READMEs and the root READMEs list the new request.
- Offline request: when you ask Claude to stay offline for a task ("stay offline", "don't go online", "send nothing out", "no network"; Turkish "ağa çıkma", "çevrimdışı kal"), skill discovery uses only the session listing and the local index. It runs no SearchSkills / SearchPlugins / connector-directory search, shows no card and does not run `dis_kaynak_ara.py`, not even the star/age check, and the task itself makes no network call. It offers no marketplace install, because it downloads from the network; a skill already on disk can still be read and followed, or copied into your skills folder after a numbered yes. Candidates that would need the star/age check are not named, and the provenance block says once that layers 3-5 were not checked.

### Changed

- Narrower description. Claude uses the skill when you ask which skill or plugin fits a task, whether one exists, or to find, recommend or install one, and when a task needs a file format, tool or service that no skill in the session's listing covers; it no longer runs before most multi-step tasks. If you did not ask about skills and a listed skill fits, Claude uses that skill directly. Trigger evaluation on a relabeled 71-query set (31 should trigger, 40 should not): Turkish edition 68/71, English 67/71; 39 of the 40 negatives correct in both.
- A third-party skill's SKILL.md from the internet is never followed manually any more; it is read only as data during the pre-install review. The layer 5 consent question has two options: 1. install persistently (community catalog: Claude installs after two separate yeses; skills.sh: you run the command) / 2. skip. Following a SKILL.md manually remains only for skills on disk (your own skills, Anthropic's official marketplace clone, a skill an MCP server you connected offers).
- The star/age check (`dis_kaynak_ara.py --repo`) runs without asking only in a task where you asked about skills or plugins. When the skill starts on its own because a task needs something no listed skill covers, it runs neither the star/age check nor a third-party search (in the Desktop Code tab or claude.ai chat it may still send a few search words to claude.ai's SearchSkills / SearchPlugins and, when a needed service has no tool in the session, up to 4 words to the connector directory search): such a candidate is not measured and not named, and the report may offer to check.
- Each plugin folder's README has new sections, the same facts in both editions: What it does, Network requests, Files it writes, Data retention, Example prompts, Privacy policy, Support (Turkish: Ne yapar, Hangi ağ isteklerini atar, Hangi dosyaları yazar, Veri saklama, Örnek istemler, Gizlilik politikası, Destek), plus an install line and the plugin ids for GitHub and claude.ai installs (the English README also gives the community-marketplace id: only `skill-sleuth` is submitted to the plugin directory, `skill-bulucu` stays on the GitHub marketplace). The directory lists that README, and users receive only the plugin folder.
- Each plugin folder carries the MIT `LICENSE`. `tools/build_yayin.py` copies it from the repository root; `--check` (and so CI) fails if a plugin folder's copy is missing or differs, and a dry run reports it as INFO.
- `.gitattributes` sets no attributes (the directory stops validating a repository whose attributes rewrite file contents). CI sets `core.autocrlf false` before checkout, so Windows runners keep LF line endings.
- `tools/build_yayin.py --zip` also writes a byte-identical `<edition>.skill` next to each `<edition>.zip`; without a folder it writes both to `dist/v<version>/` (git-ignored). `dist/` is left out of the tree checks.
- `skill_ara.py`: the cache's roots record keeps only the four roots it compares (no current folder and no list of the parent folders it searched), and entries carry no separate `synced_bucket` field; project skill folders that exist, the `~/.claude` path and the Desktop / sync folder names inside stored paths remain, as the plugin README says. A `--cache` / `$SKILL_ARA_CACHE` path that does not end in `.json`, lies in a Claude config tree or holds a file that is not its index is not used (one `not:` line; the index is built in memory); the file is checked only after its folder, without blocking on a FIFO.
- All four scripts share a new `claude_tree()` check: no cache or output file is ever written into a `.claude` folder, `~/.claude.json`, `$CLAUDE_CONFIG_DIR` or `$CLAUDE_CODE_PLUGIN_CACHE_DIR` (compared case-insensitively), and no folder is created there; `dis_kaynak_ara.py --cache-dir` pointing there stops with exit 2.
- `katalog_indeksle.py` no longer starts `git` to read a marketplace clone's HEAD (nothing used it): no script starts another program. It and `skill_envanteri.py` now pass everything they print through `scrub()` (an invisible or bidi character shows as `?`, as in `skill_ara.py`); `katalog_indeksle.py` also strips them from descriptions and adds `GIZLI-KARAKTER(<n>)` to one that hid 8 or more.
- `skill_envanteri.py` no longer scans Cowork scheduled tasks, Cowork session uploads or `~/.codex`, and never opens Claude Desktop's own config file; another folder can still be added with `--extra-root`.
- `dis_kaynak_ara.py`: the two references it points to are named for the edition it runs in (`security-checklist.md` / `security-review-details.md` in the English edition).
- The pre-install review no longer runs `git ls-remote` against a candidate's repository; a `ref` without a `sha` is read from the catalog entry.
- Wording in the skill references: "no other script goes online" (Claude itself may read a candidate's public files during the pre-install review, and the READMEs now say so); starting a separate `claude -p` process with a temporary command file needs a numbered yes; the pre-install review record stays in the conversation, not in a file; a missing `pyyaml` is reported with the `pip install pyyaml` command for the user to run. The scripts README says the scripts keep only SKILL.md frontmatter, that only a symlinked cache file (not folder) is refused, and runs the inventory diagnostic with its default output folder. The root READMEs describe the cache folder and Claude's own requests more precisely, and SECURITY.md names the output locations you can choose (`--out`, `--cache-dir` or `$DIS_KAYNAK_CACHE_DIR`, and the folder of the `--cache` / `$SKILL_ARA_CACHE` file).

### Fixed

A code review of the publish tree, and a second review of the fixes, found that the local index sometimes disagreed with what Claude Code actually loads. `skill_ara.py` (0.6.2; 0.6.3 in this release) now follows the loading rules of Claude Code 2.1.295 (`skill_envanteri.py` and `katalog_indeksle.py` use the same rules); the last fix below follows a change in the Claude desktop app:

- Settings are read like Claude Code reads them: `enabledPlugins`, `skillOverrides` and `disableBundledSkills` merged from `~/.claude/settings.json`, the project's `.claude/settings.json` and `.claude/settings.local.json` (on macOS and Linux also the git root's `settings.local.json`), later wins. A plugin installed with `--scope local`, the skill's own default, is no longer reported as not usable; a plugin switched off only in this project is no longer offered as callable; a user, project or bundled skill set to `off` or `user-invocable-only` in `/skills`, and the bundled skills under `disableBundledSkills`, are no longer offered as `Skill(<name>)` (`CLAUDE_CODE_DISABLE_BUNDLED_SKILLS` and `CLAUDE_CODE_RESTRICT_PERSONAL_CONFIG` count as set only for 1 / true / yes / on). The cache is rebuilt when these values change.
- Only the plugin-cache folder Claude Code uses in this folder counts as installed: the `installPath` of the first install record that applies here (user scope, or a project / local record of this project), without an `.orphaned_at` marker. A folder an update, an uninstall or another project's install left behind no longer shows old skills as callable or proposes `claude plugin enable` for a removed plugin. The plugin id comes from `installed_plugins.json`, so a plugin whose name has a dot (its cache folder name is sanitized) is no longer lost.
- A plugin's skills are found where Claude Code finds them: the default `skills/` folder and the plugin.json `skills` paths together; the plugin's marketplace entry (a root `./` source keeps only its listed skills; without plugin.json the entry's skills replace the manifest's; a `strict: false` entry that declares components next to a plugin.json makes Claude Code refuse the plugin, and the index says so); a skill path that leaves the plugin folder is ignored; a skill path that holds its own `SKILL.md` (named by its frontmatter name); a `SKILL.md` at the plugin root when there is nothing else; names with characters outside `[A-Za-z0-9_-]` turned into `-`.
- A `SKILL.md` deeper than `<skills dir>/<name>/SKILL.md` is listed only with `--all`, as not loaded, except in a folder of your skills dir that holds `.claude-plugin/plugin.json`: Claude Code loads it as a plugin `<name>@skills-dir` (name = its plugin.json name, else the folder; the layout `claude plugin init` writes), and so does the index (`<plugin>:<skill>` and `<plugin>:<command>`; `enabledPlugins` `<name>@skills-dir: false` switches the folder off, and plugin.json `"defaultEnabled": false` keeps it off until `enabledPlugins` says true).
- Project skills: the current folder and its parents up to the git root are all loaded and callable (parents were listed as unverified); outside a repository the walk goes up to the filesystem root but never includes the home folder; in a git worktree without its own `.claude/skills`, the main checkout's folder is used.
- A skill seen only in a marketplace clone is never listed as callable (Claude Code loads plugins from the plugin cache only); its hint is install, enable or update, by the plugin's state, and a clone copy of a skill the installed version also has is left out, so it can never replace the callable copy.
- An installed official-catalog plugin with no skill (MCP, LSP or hooks only), and a plugin in the marketplace clone that ships no `SKILL.md`, appear in searches again; an installed and enabled one is no longer offered for installation, and `--show <plugin>` of an installed and enabled plugin says there is nothing to install.
- JSON files saved with a byte order mark (`settings.json`, `plugin.json`, `installed_plugins.json` ...) are read instead of being treated as empty.
- Search: a capital `İ` no longer splits a word (`İncele` matches like `incele`), and three-letter stems no longer make unrelated words equal (`date` no longer ranks the `data` skills first) while `code` / `coding` and `type` / `typing` still match. The both-editions note no longer counts a nested copy that Claude Code does not load.
- `dis_kaynak_ara.py` 0.4.2: a GitHub outage (HTTP 5xx) is reported as `GitHub ulasilamadi` and `--repo` exits with 3, instead of "repository not found" with the install command removed, and a failed or timed-out per-path history request no longer hides the file list and stars; hidden characters are counted in the frontmatter values, the SKILL.md path and the file names next to it, audit fields and the catalog's name, source, homepage, author, category and content paths (also in `--audit` and for eliminated hits), not only in the description; the plugin content line of `--show community:<plugin>` names `monitors/monitors.json`, `.lsp.json` and `settings.json`; a malformed audit or install count from skills.sh no longer stops the script with a traceback.
- `skill_envanteri.py` gives no Skill-tool name to marketplace-clone copies or switched-off skills, lists claude.ai synced skills as `user-synced` instead of `user`, and no longer stops when a plugin's skill path is on another drive or a plugin.json name is not a string; `katalog_indeksle.py --search` prints install, enable or nothing by the plugin's state, counting only install records that apply in the current folder; `tools/build_yayin.py` reads a private pattern file saved with a byte order mark.
- The plugin READMEs (privacy policy) also name what Claude reads without asking to tell the Desktop app, a terminal and an unattended run apart (four environment variables, the session file and two manifests), and the `.git` entries the scripts check to find the git root.
- The Claude desktop app moved its data folder on Windows (observed 2026-10-22): `%APPDATA%\Claude` and the MSIX folder `%LOCALAPPDATA%\Packages\Claude_<suffix>\LocalCache\Roaming\Claude` keep only an empty marker file, the data now lives in `%LOCALAPPDATA%\Claude-Data\<id>\`, and the claude.ai plugin cache moved from `local-agent-mode-sessions\<account>\<org>\rpm\` to `rpm\<acct8>\<org8>\` in that folder (the first 8 hex digits of the ids), so the index found neither the desktop skills nor the claude.ai plugin skills. `skill_ara.py` 0.6.3 and `skill_envanteri.py` now take the first of `%APPDATA%\Claude`, `%LOCALAPPDATA%\Claude-Data\<id>` (of several, the one whose `local-agent-mode-sessions` changed last) and the MSIX folder that holds `local-agent-mode-sessions`, else `%APPDATA%\Claude` as before, and read claude.ai plugins from `<desktop data folder>\rpm\<acct8>\<org8>\` as well as from the old place (on every OS); `$CLAUDE_DESKTOP_DATA_DIR` still decides when set, and the macOS and Linux data folders are unchanged. The version change rebuilds the index cache, and so does a plugin cache that appears or changes.
- Not yet covered: commands in sub-folders of a plugin's `commands/` (Claude Code names them `<plugin>:<folder>:<name>`), a plugin.json `commands` key that replaces the default folder, and skills-dir folders that the claude.ai sync manifest claims.

## 0.1.0 — 2026-10-09

Prepared but not published as a release; 0.1.1 is the first public release.

### Added

- Two language editions of the same skill, shipped as two plugins in one marketplace: `skill-bulucu` (Turkish) and `skill-sleuth` (English, translation of the Turkish edition). They share byte-identical scripts and `builtins.json`; a user installs one of them. The local index never lists the skill itself (either edition, any tier) and adds a one-line note to its output when both editions are installed at once.
- Five discovery layers, searched in order; layers 3-5 are skipped when a skill already in this session's listing covers the whole need: session listing; offline local index (`scripts/skill_ara.py` 0.6.0, 10 on-disk tiers, 2 KB output cap, automatic cache rebuild); claude.ai `SearchSkills` / `SearchPlugins` (Claude Desktop Code tab, and claude.ai chat when its tools are offered); MCP `skill://` resources; third-party registries (`scripts/dis_kaynak_ara.py` 0.4.0: skills.sh and the `claude-community` catalog), consent-gated.
- Per-candidate signals for everything not installed: author's description, source repo and pinned commit, install count, GitHub stars, repo age and last update, labels.
- Protection rule with labels `YENI` (< 90 days), `AZ-KURULUM` (< 1,000 installs), `AZ-YILDIZ` (< 100 stars), `BAYAT` (> 365 days without update), `ARSIV`, and five elimination cases; the fifth covers a source with no install counter (e.g. the community catalog), where `AZ-YILDIZ` or stars that could not be verified (GitHub limit or outage, request budget, no GitHub repository of its own) eliminate a candidate. Eliminated candidates are listed with their reason, never recommended; the `YENI`, `AZ-KURULUM` and `AZ-YILDIZ` thresholds are flags (`BAYAT` is fixed at 365 days), non-default values print a note.
- Trust wording per registry, printed by `dis_kaynak_ara.py` and shown with every third-party candidate: the `claude-community` catalog is "scanned and approved by Anthropic; it does not vouch for the code" (its entries passed Anthropic's automated security scan and were approved for the catalog); skills.sh is "not reviewed by Anthropic".
- Consent model: numbered dialog after a review block for every install, enable, `~/.claude/skills/` copy or settings change; consent per plugin and per scope; third-party search needs its own consent, third-party use a second one; Claude never runs a third-party skill's own scripts or hooks; a community-catalog plugin pinned to a commit is installed by Claude only after two separate consents, a skills.sh install command only by the user.
- Unattended mode: in `claude -p`, Agent SDK, scheduled-task, routine, workflow or subagent runs nobody can answer, so the skill asks no questions, installs or enables nothing and skips third-party search (layer 5); it uses only skills already available and lists what it would have proposed under Persist.
- Privacy guard in `dis_kaynak_ara.py`: only three hosts, read-only GET, no tokens; query shape validated before any request; local paths, file names and inventory never leave the machine. The star/age check (`--repo`) for a not-installed catalog candidate needs no search consent; only the public repo name goes out.
- Cache location: `%TEMP%\skill-sleuth` on Windows, `~/.cache/skill-sleuth` on macOS/Linux (`$XDG_CACHE_HOME/skill-sleuth` if set, mode 0700). On macOS/Linux a cache folder or file owned by another user, writable by group/others or symlinked is not used. The scripts never write into the skill folder.
- Provenance block at the end of every run (Mode, Needs, Candidates, Chosen, Obtained, Skipped, Eliminated, Persist).
- Python lookup: the skill tries `python`, then `python3`, then (on Windows) `py -3`; if `python` is Python 2, it uses `python3`; if only the `py` launcher works, it calls its scripts with `py -3`. Without any Python 3.9 or later it skips the local index (layer 2), third-party search (layer 5) and the star/age check, goes on with the other layers and says so on the Skipped line.
- Diagnostic scripts `katalog_indeksle.py` and `skill_envanteri.py` (offline), `builtins.json` sidecar (names of the built-in skills of one Claude Code version, each with a short keyword summary written for the index).
- Windows 11 verified (desktop app Code tab and npm CLI). Task evaluations on the release text: 14 scenarios (10 Turkish, 4 English) passed 91 of 95 checks on the first run; the three affected scenarios re-ran at 19 of 20 after their root causes were fixed (the last miss, a catalog date the model inferred, is answered by the new `catalog_fetched_at` field of `skill_ara.py --show`). Trigger evaluation with the final names, 63 queries per edition (the earlier 49 plus 8 ordinary coding tasks and 6 indirect English requests), one run each: 62/63 (Turkish) and 59/63 (English); every miss passed 3 of 3 when re-run, so the misses were single-run noise. As its description asks, the skill also runs before ordinary multi-step coding tasks; task eval 20 shows that it then asks nothing, searches no registry and ends with a three-line report.
- Repository tooling: `tools/build_yayin.py` assembles the plugins from the source skill folders and fails on personal-data patterns, size limits, CRLF/BOM, unexpected frontmatter keys, script drift between the two editions and version drift (each `plugin.json` must equal its `marketplace.json` entry and the top heading of this file). Machine-specific patterns are read from a private file kept outside the repository. `--check` runs the same checks on the tree as it is, for a clean clone without the source folders (chosen automatically there); `--zip DIR` writes reproducible release zips (sorted entries, fixed timestamps and file modes) and prints their SHA-256.
- CI (`.github/workflows/ci.yml`): Ubuntu, macOS and Windows × Python 3.9 and 3.12, read-only permissions, actions pinned to commit SHAs. It runs `tools/build_yayin.py --check` and the offline unit tests in `tests/` (standard library only; each test builds a throw-away home folder and sends no request).
- Repository files: bilingual README, SECURITY.md, a bug-report issue form, a README in each plugin folder and in `tests/`, `repository` in both `plugin.json` files.

### Known limitations

- The English edition is a translation of the Turkish one (same rules, same scripts); 8 English task scenarios have been run (4 of them on the release text), against 20 Turkish ones. Trigger results are one run per query (misses re-run three times).
- macOS and Linux paths exist in the scripts but were only tested with synthetic directory trees; the `python3` and `py -3` fallbacks are untested.
- GitHub is queried unauthenticated (60 requests/hour per IP, shared machine-wide); no authenticated mode.
- The skill itself is new and has few stars and installs, so its own protection rule would eliminate it when found through a registry.
- In claude.ai chat (web and the desktop app's chat; recognised by the skill's own path under `/mnt/skills/`) the skill runs none of its scripts (they would run in claude.ai's cloud sandbox, not on the user's computer) and does no third-party search; layer 3 is used there only when its tools are offered. On claude.ai and in the desktop app's chat, Claude picked task skills directly and did not start this skill on its own in the owner's tests; named in the message, it ran there and reported correctly.
- `builtins.json` lists the built-ins of one Claude Code version (17, 2.1.293) with keyword summaries written for the index, not the skills' own descriptions; newer built-ins are missing until it is updated.
- Install was verified on 2026-10-09 from a local copy of this repository, in an isolated config folder, with Claude Code 2.1.293 and 2.1.217: `plugin validate --strict`, `marketplace add`, `install` of each plugin, `details`, `uninstall`, and `--plugin-dir`; with 2.1.293 also `disable`, `enable`, `marketplace update`, `update` and `marketplace remove`. That was before the plugins got their final names and before the last script changes; it has not been repeated since. The `owner/repo` form is untested until the repository is public. `npx skills` discovery of `plugins/<plugin>/skills/<skill>/` was checked by reading the CLI source (it reads `.claude-plugin/marketplace.json`), not by running it.
- Claude Code does not stop a user from installing both editions; the skill's local index prints a one-line note when both are installed.
- Catalog install counts come from the official marketplace catalog cache; the community catalog has no install counter, so its entries are judged by stars and age alone, and one whose stars cannot be verified is eliminated.
